Cyclo Brain Policy Runtime
Architecture Refactoring: Detailed Report

Based on the code implemented in the current working tree, this report explains the differences from the previous architecture, each module's responsibilities, inference data flow, deployment impact, verification results, and remaining risks.

Key Conclusions

Previously, the LeRobot and GR00T containers each owned not only model inference but also the action buffer, control cycle, robot command publishing, and safe stopping. The shared control layer has now moved to the central Policy Runtime in the Cyclo container, and the model containers have been reduced to Engine-only Workers.

CentralizedOne Control Layer

Cyclo provides a single implementation of the session, ControlLoop, action chunk processing, initial pose sync, and safe stopping.

IsolatedSeparate Model Workers

LeRobot and GR00T handle only framework dependencies, model loading, observation preprocessing, and inference.

Catalog-drivenUnified Policy Information

The policy list, capabilities, and UI parameters are declared in manifests, and the UI and Supervisor use the same catalog.

The overall assembly point. It creates Catalog, WorkerRegistry, SessionState, ControlLoop, and ServiceHandler, then starts the central service, heartbeat subscriber, and UDS server. On shutdown, it attempts the fail-safe first.

Executes the LOAD/START/PAUSE/RESUME/STOP/UNLOAD/STATUS state transitions. It validates the policy ID and parameters, selects a Worker, and configures ControlLoop after LOAD succeeds.

Where the Data Goes

Control requests, observations, action chunks, and robot commands follow different paths.

Control request

From UI to Model Execution

UI → Orchestrator → Policy Runtime → Worker. Only small lifecycle requests and action chunks pass through services.

Observation

From Robot to Model

Robot topic → Worker RobotClient → preprocessing. This path does not pass through Cyclo.

Command

From Model Output to Robot

Worker action chunk → Runtime buffer/interpolation → Cyclo RobotClient → command topic.

Why the main_runtime Name Remains

The directory name remains because the existing shared runtime was reused, but it runs in Cyclo, not in a Worker. The actual s6 service is named policy-runtime; it is not a functionally duplicated runtime.

Removed Worker Service

The main-runtime s6 definition was removed from LeRobot and GR00T. Worker healthchecks now check engine-process and the ready marker.

Objective Improvements and Remaining Risks

A new architecture is not inherently an improvement. Duplication, deployment, communication, fault isolation, and operational complexity are assessed separately.

Improvement

Eliminate Shared Control Duplication

ControlLoop and safety are no longer duplicated in every Worker, so the benefit grows with the number of models.

Improvement

Unified Command Ownership

A single global session and one Runtime publish commands, preventing control contention between backends in one place.

Improvement

Fewer UI Changes When Adding Models

Policy display, instructions, and parameters have moved into manifests, reducing hardcoded React/Python configuration.

Improvement

Reproducible Deployment Images

Removing source mounts from the default Compose configuration reduces the risk of a host checkout implicitly changing an image's behavior.

Cost

Container Hop for Action Chunks

Small numeric arrays move from Workers to Cyclo. This costs less than relaying images, but latency still needs to be measured.

Cost

Protocol Compatibility Management

Changes to EngineCommand require coordinated management of Cyclo and Worker version combinations.

Status Directly Verified So Far

Verified
Three containers
cyclo_intelligence, lerobot_server, and groot_server are healthy on AMD64.
Verified
Catalog and Worker contract
The live API returns both manifests, and both Workers are compatible with protocol 1.0.
Verified
LeRobot ACT action path
Live robot topics were received from three cameras and joint_states at approximately 14 Hz, and a direct GET_ACTION call to the Engine returned a 100 x 22 chunk.
Needs Fix
Sensor readiness
LeRobot loading ignores wait_for_ready() failures, so it can succeed even when joint data is temporarily unavailable. It waits for all configured cameras and also warns about cam_right_head, which the policy does not use.
Needs Fix
Worker status timeout
DESCRIBE queries can hit a two-second timeout while the model is busy. This is separate from action timeouts, but the status path needs to be made nonblocking or cache-based.
To Validate
ARM64 and real GR00T
Completion requires verifying LOAD with a real checkpoint, observations, action chunks, and faults on the target robot.

Conclusion: This architecture is better suited than the previous one to adding multiple models quickly and frequently changing shared inference features. However, deployment must not be considered complete until sensor readiness and status timeouts are addressed and ARM64, GR00T, and real fail-safe validation have passed.
