Cyclo Brain / Current Operating Architecture

Central Policy Runtime and
Engine-only Worker

The Cyclo image owns inference control, while Worker images own model dependencies and inference execution. This document describes the processes, communication, safety boundaries, and file locations in the current code.

Overview

Policy Runtime is not a model. It is the central control layer responsible for the global inference session, action processing, robot commands, and safety. Workers receive camera data and state directly and return only model action chunks.

Explicit Contract

Engine Protocol

DESCRIBE, LOAD, GET_ACTION, STATUS, and UNLOAD separate implementations from control logic.

Compatibility: The Python package name main_runtime is retained for compatibility with existing imports, but the Worker's s6 main-runtime service has been removed. This package runs only in the Cyclo image's policy-runtime service.

Command and Data Flow

LOAD and START

UI / BT creates TaskInfo

It includes policy_id, checkpoint, timing, initial pose sync, and model parameters.

Orchestrator calls the central Runtime

It checks JSON syntax and sends LOAD or START to /policy/inference_command.

Runtime validates the catalog and Worker

LOAD proceeds only if the manifest schema, Worker DESCRIBE, protocol major version, capability, and heartbeat all pass validation.

Worker collects observations directly and runs inference

Runtime does not forward images or general sensor data to Workers.

Runtime processes and publishes actions

ActionChunkProcessor and ControlLoop interpolate and buffer actions, then send commands through RobotClient.

Topic Subscription Ownership

Worker

Always: Subscribes to the images, state, and sensors required by the model.

Policy Runtime

Active session on a physical robot: Subscribes only to the joint state needed for hold and freshness checks.

Cyclo Data

During recording: Subscribes separately for data acquisition. This duplication is intentional because its purpose differs from inference.

Important: No Gateway was introduced to collect observations in the central Runtime and retransmit them to Workers. This avoids adding another stage of image serialization and intermediate copying.

State and Safety Boundaries

A safe stop takes priority over a successful service response. Until hold is confirmed, the session is not marked as having ended normally, and the Worker is not shut down.

READYNo Worker selected, or unloaded
LOADEDWorker and policy compatibility validated
SYNCINGOptional initial pose sync
RUNNINGAction loop and robot commands active
PAUSED / ERRORHold succeeded or awaiting a safe stop

Failure Detection

Monitoring covers loss of Worker heartbeat, loss of Orchestrator heartbeat, action timeouts, Worker instance replacement, and protocol mismatches.

Fail-safe Sequence

Processing follows this order: clear the action buffer → zero Twist → hold the current pose using fresh joint state → transition state.

Lifecycle interlock

While inference is active or hold is pending, Supervisor's Worker stop/restart/recreate/update operations are rejected at the UDS lease stage.

System Boundaries

The application cannot guarantee hold during forced power loss, Docker daemon termination, or kernel failure. A command watchdog in the robot controller is essential.
