Cyclo Brain / Current Operating Architecture

중앙 Policy Runtime과
Engine-only Worker

인퍼런스 제어는 Cyclo 이미지가 소유하고, 모델 의존성 및 추론은 Worker 이미지가 소유합니다. 이 문서는 현재 코드의 프로세스, 통신, 안전 경계와 파일 위치를 설명합니다.

전체 구조

Policy Runtime은 모델이 아닙니다. 전역 inference session, action 처리, 로봇 명령과 안전을 담당하는 중앙 제어 계층입니다. Worker는 카메라와 state를 직접 받아 모델 action chunk만 반환합니다.

중앙 Runtime

모든 정책은 동일한 lifecycle과 안전 동작을 거칩니다. 동시에 하나의 inference session만 허용합니다.

직접 관측

Engine-only Worker

이미지/state는 Worker가 Zenoh topic을 직접 구독하므로 중앙 Runtime이 대용량 관측을 중계하지 않습니다.

명시적 계약

Engine Protocol

DESCRIBE, LOAD, GET_ACTION, STATUS, UNLOAD로 구현체와 제어 로직을 분리합니다.

호환성: Python package 이름 main_runtime은 기존 import 호환을 위해 유지하지만, Worker의 s6 main-runtime 서비스는 제거되었습니다. 해당 package는 Cyclo 이미지의 policy-runtime 서비스에서만 실행됩니다.

Policy Runtime 책임

하나의 Python 프로세스 안에서 아래 객체들이 역할을 나눕니다. 각각이 별도 서비스라는 뜻은 아닙니다.

모듈입력책임출력
MainRuntime
main.py		catalog, 환경 설정공통 객체를 조립하고 중앙 서비스, heartbeat, UDS control server를 시작/종료/policy/inference_command 및 alias
ServiceHandler
service_handler.py		InferenceCommand명령 검증, Worker 선택, session 전환, load/start/stop/unload 순서 보장상태가 포함된 response
SessionState
session_state.py		검증된 상태 전환단일 session의 policy, runtime, phase, signature, error를 메모리에 보관명령 허용 여부와 snapshot
WorkerRegistry
worker_registry.py		manifest + DESCRIBEpolicy prefix로 Worker를 찾고 protocol, policy set, capability, heartbeat를 검증호환 가능한 Worker client
InferenceRequester
inference_requester.py		LOAD/GET_ACTION payloadEngineCommand 생성, timeout과 seq_id 처리, 한 번에 하나의 action 요청 유지정규화된 action chunk
ControlLoop
control_loop.py		action chunk + timingbuffer 보충, 보간, control tick, sync/async, initial pose sync, pause/stop holdRobotClient command
RuntimeControlServer
runtime_control.py		로컬 UDS 요청Supervisor가 Worker mutation 전 lease를 얻도록 하고 active/hold-pending 작업을 차단허용/거부 및 lease token

Engine-only Worker

Worker는 framework 의존성과 모델 실행만 소유합니다. 제어 주기, action buffer, 로봇 명령, pause/stop 안전 상태는 Worker에 두지 않습니다.

명령과 데이터 흐름

LOAD 및 START

UI / BT가 TaskInfo를 생성

policy_id, checkpoint, timing, initial pose sync, 모델 파라미터를 포함합니다.

Orchestrator가 중앙 Runtime을 호출

JSON 문법을 확인하고 /policy/inference_command에 LOAD 또는 START를 전달합니다.

Runtime이 catalog와 Worker를 검증

manifest schema, Worker DESCRIBE, protocol major, capability, heartbeat가 모두 맞아야 LOAD합니다.

Worker가 observation을 직접 수집하고 추론

Runtime은 이미지나 일반 센서를 Worker로 전달하지 않습니다.

Runtime이 action을 처리하고 발행

ActionChunkProcessor와 ControlLoop가 보간·버퍼링한 뒤 RobotClient로 명령을 보냅니다.

토픽 구독 소유권

Worker

항상: 모델에 필요한 image, state, sensors를 구독합니다.

Policy Runtime

실제 로봇 active session: hold와 freshness 확인에 필요한 joint state만 구독합니다.

Cyclo Data

녹화 중: 데이터 취득을 위해 별도 구독합니다. inference와 목적이 달라 중복은 의도적입니다.

중요: 관측을 중앙 Runtime으로 모아 Worker에 재전송하는 Gateway는 도입하지 않았습니다. 따라서 이미지 직렬화와 중간 복사가 한 단계 늘어나지 않습니다.

상태와 안전 경계

안전 정지는 “서비스 응답 성공”보다 우선합니다. hold가 확인되지 않으면 session을 정상 종료 상태로 표시하거나 Worker를 내리지 않습니다.

READYWorker 미선택 또는 unloaded
LOADEDWorker 및 policy 호환 검증 완료
SYNCING선택적 initial pose sync
RUNNINGaction loop와 robot command 활성
PAUSED / ERRORhold 성공 또는 안전 정지 대기

실패 감지

Worker heartbeat 단절, Orchestrator heartbeat 단절, action timeout, Worker instance 교체, protocol 불일치가 감시 대상입니다.

Fail-safe 순서

action buffer 삭제 → zero Twist → fresh joint state 기반 현재 자세 hold → 상태 전환 순으로 처리합니다.

Lifecycle interlock

active inference 또는 hold pending이면 Supervisor의 Worker stop/restart/recreate/update를 UDS lease 단계에서 거부합니다.

시스템 경계

강제 전원 차단, Docker daemon kill, 커널 장애는 애플리케이션이 hold를 보장할 수 없습니다. 로봇 제어기 command watchdog이 필수입니다.

Container

docker-compose.yml은 image 내용을 기준으로 실행하며 runtime/UI/Supervisor source bind mount를 사용하지 않습니다.

Local iteration

코드 변경은 해당 image를 --build로 다시 만들고, UI만 바꿀 때에는 container.sh build-ui로 정적 파일을 교체합니다.
