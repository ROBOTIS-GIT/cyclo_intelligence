# ArUco docking — Gazebo first-stage test

`ArucoDock` is a local image-feedback BT action for the FFW-SG2 holonomic base.
It does not plan a route. Start within 3.5 m, facing a visible marker in a clear
approach area, after stopping Navigation/teleop/inference that commands the base.
Only one docking action may own the base in a Task Engine process.

## Simulation markers

The `home_autonomy` world includes `home_aruco_docks` below the north-wall clock.
From inside the room, left to right: **10, 11, 12**, `DICT_4X4_50`.
Each marker's outer black square is **0.30 m**; white board is 0.40 m.
Centres: `(0.55, 6.875, 1.10)`, `(1.35, 6.875, 1.10)`, `(2.15, 6.875, 1.10)`.
Faces point toward -Y. Small digits below each board identify the marker.
Change `marker_id` to dock to each marker individually; this is not a three-marker
pose-fusion algorithm. The selected marker must be visible.

Assets are generated by `ffw_bringup/tools/build_home_aruco_docks.py` using the
actual OpenCV dictionary. Geometry avoids external texture path problems.

## Canvas usage

Start Task Engine and refresh its node catalog. Add **ArucoDock** to a Sequence
in Action Canvas or a waypoint's local BT in Mission Canvas. No Qwen is needed.
An example lives in `orchestrator/orchestrator/bt/trees/aruco_dock_10.xml`:

```xml
<root BTCPP_format="4" main_tree_to_execute="MainTree">
  <BehaviorTree ID="MainTree">
    <ArucoDock name="DockToMarker10" marker_id="10" marker_size="0.30"
               target_distance="0.85" timeout="120" />
  </BehaviorTree>
</root>
```

- `target_distance`: metres from **base_link origin to marker face**, not camera.
- `position_tolerance`: XY error norm, default 0.035 m.
- `yaw_tolerance`: radians, default 0.06 (~3.4 degrees).
- `max_speed`: combined XY speed limit, default 0.10 m/s (maximum 0.20).
- `max_yaw_rate`: default 0.18 rad/s.
- `min_speed` / `min_yaw_rate`: 0.035 m/s / 0.04 rad/s outside the pose
  tolerance, to exceed the simulation swerve controller's 0.03 component
  deadbands. Inside tolerance the command is zero. These values do not alter
  Navigation or the underlying controller configuration.
- `stable_seconds`: 0.7 s and at least five separate valid frames, with low odometry
  velocity, before SUCCESS.
- `timeout`: 120 s wall time, excluding acknowledged pauses.
- `lost_timeout`: 3 s without usable feedback before FAILURE. Motion stops
  immediately on an unusable observation; it never drives blind to find a marker.

Transport defaults (editable ports): `/zed/left/image_raw`,
`/zed/left/camera_info`, `/scan`, `/odom`, `/cmd_vel`, `base_link`.
These are the simulation topics; real-camera topics/calibration must be configured
and verified before any physical-robot deployment. The raw Image and CameraInfo
must agree on resolution and optical frame. Distorted images use K and D directly.

## Implementation

- `bt/docking_vision.py`: OpenCV 4.6+ detection, ID selection, solvePnP,
  reprojection screening and optical-frame → base-frame transforms.
- `bt/docking_core.py`: marker-normal target pose, bounded holonomic feedback,
  conservative footprint/scan clearance checks.
- `bt/docking_runtime.py`: lazy ROS inputs, image-time TF lookup, timestamp and
  receipt freshness, worker/watchdog, status/preview, acknowledged pause and Stop.
- `bt/actions/aruco_dock.py`: editor ports, lifecycle and BT result.

The face normal is marker +Z. The target lies `target_distance` along that normal
and faces back toward the marker. No known Gazebo marker/world coordinates are
used by the controller. Translation waits when heading error exceeds 0.45 rad.
The exact image-time TF is awaited for up to 0.12 s to accommodate sensor/TF arrival
order; no latest-TF fallback is used. Stale images, odometry, scan, invalid poses,
obstacles or missing markers stop commands. An active NavigateToPose goal rejects
docking. This is local test control, not a certified collision-avoidance system.

## Diagnostics

- `/bt/aruco_docking/status`: JSON with marker ID, phase, error `[x,y,yaw]`, detail.
- `/bt/aruco_docking/debug_image`: selected marker outline and docking error.

Completion requires both geometry and stationary odometry. A successful RESUME
of a VLA is not used as evidence of docking success.

Docking clearance: circular radius 0.43 m + 0.04 m margin + 0.5 s translation lookahead. At 0.035–0.10 m/s the forward check reaches 0.4875–0.52 m. A 0.55 m target is the next simulation test setting; accepting a 0.35 m parameter does not bypass this collision guard. Close-range operation remains unvalidated.

## Rectified docking images

ArucoDock always detects markers in rectified pixels and estimates pose using
CameraInfo.P's left 3x3 matrix with zero distortion. `image_mode="raw"` (default)
rectifies the existing image topic internally using K, D, R and P; maps are cached.
Existing Gazebo missions need no edits. `image_mode="rectified"` skips remapping;
select the matching rectified image and CameraInfo topics together. For ZED the
left rectified topic may be `/zed/zed_node/left/image_rect_color`; verify the driver
CameraInfo topic and calibration before use. Do not apply raw mode to rectified
images, as that would correct distortion twice. Rectified pose is transformed
back using R transpose before the camera-to-base TF. Full-frame left/monocular
calibration is required; ROI/binning and right stereo P translations are rejected.
The debug image is now rectified. Close-range docking remains subject to visibility
and collision checks; rectification does not recover cropped or occluded markers.

## Failure diagnostics

On failure, up to 32 recent frames (sampled at 5 Hz) and 160 bounded diagnostic
events are saved under `docker/workspace/logs/aruco_docking/<UTC-time>_marker_<ID>_<suffix>/`.
`report.json` contains sensor image timestamps, camera calibration, marker size,
detected IDs, target corners, minimum edge pixels, border margin, reprojection RMS,
pose errors/commands when available, and the final failure reason. Each retained
frame has raw, rectified and annotated PNGs when available. Image files are written
asynchronously after issuing zero velocity. Write errors are logged separately and
do not change motion behavior. `CYCLO_DOCK_DIAGNOSTICS_DIR` overrides the directory.
No image is invented for missing camera input; in that case inspect the JSON events.
No detection thresholds or loss timeout were relaxed by this diagnostic change.


### SG2 footprint and post-task retreat

`ArucoDock footprint_profile="sg2_autonomy_base"` opts into the Autonomy Studio
SG2 base-and-wheel top-view convex envelope, in metres relative to `base_link`.
Its front is +0.2246 m, rear -0.4029 m and sides ±0.301 m. This is the Studio
silhouette geometry, **not** Nav2's published circular footprint or a live arm
envelope. Nav2 settings are unchanged. Other actions default to `circle`.
The guard checks translation and rotation over 0.5 s with 1 cm clearance;
sampling adds a motion bound to cover the gaps. Blocking scan coordinates and
commands are included in failure diagnostics.

After inference STOP and arm retraction, use:

```xml
<DockRetreat distance="0.20" speed="0.05" timeout="20"
             footprint_profile="sg2_autonomy_base"/>
```

Retreat uses initial-heading odometry progress, fresh rear laser coverage,
obstacle checks, a command watchdog, and stationary confirmation before success.
It pauses/stops through the same base-ownership lifecycle as docking; stale or
blocked sensing holds at zero and fails after 3 seconds. It does not execute
Nav2 or start inference. Distance is measured from retreat start, not the marker.
The 20 cm distance is a simulation test setting, not a guarantee of clearance
for arbitrary arm poses or physical robot payloads.

### Departure ownership: explicit BT action

Post-docking departure belongs to the mission's local BT, not the default
Navigation BT. Add `DockRetreat` from the Action Canvas action catalog after
arm retraction and before `ReturnToWaypoint` (or before the local BT completes
and the mission runner advances to its next waypoint). Use a normal Sequence
so retreat failure prevents navigation. Do not wrap departure in a force-success
node.

```xml
<Sequence name="DepartDock">
  <!-- Stop inference and return the arms to the travel pose first. -->
  <DockRetreat name="LeaveDock" distance="0.20" speed="0.05"
               timeout="20" footprint_profile="sg2_autonomy_base"/>
  <ReturnToWaypoint map_name="house" mission_name="ArUcoDockTest"
                    waypoint="house_aruco_start_11" timeout="300"/>
</Sequence>
```

`house/ArUcoDockTest` already includes separate RetreatAfter10, RetreatAfter11
and RetreatAfter12 nodes. Tune their distance/speed independently in the canvas.
No persistent dock-state flag or automatic departure plugin is enabled in Nav2.
The ordinary Nav2 recovery BackUp is separate and remains available.

Pause/resume preserves the running retreat's origin and progress. Stop/reset
ends that action; executing it again starts a new relative retreat from the new
position. This is intentionally not an automatic resume of a previous departure.

The independent near-goal Omni controller selection remains a Navigation
responsibility; it does not trigger a dock retreat.

### Docking resolution: VGA / HD720

`ArucoDock camera_profile="VGA"` (default) detects at **672x376**;
`camera_profile="HD720"` detects at **1280x720**. The UI exposes these two choices.
The selected size is a detection resolution, not a command to restart the ZED.
The node never upscales a smaller source. It reports the required/source sizes
when an insufficient image is supplied. Diagnostics record both source calibration
and the actual detection resolution/intrinsics.

Leave both `image_topic` and `camera_info_topic` empty for automatic selection:
- SG2 simulation: the dedicated `/zed/left/high_resolution/image_raw` and
  `/zed/left/high_resolution/camera_info` pair, rectified internally.
- Physical ZED: `/zed/zed_node/left/image_rect_color` and
  `/zed/zed_node/left/camera_info`, already rectified.
Explicitly setting both topics overrides automatic selection; set `image_mode`
according to that source. Other ZED namespaces need explicit topic paths.

SG2 Gazebo renders the head at 1280x720; the docking node downsamples to VGA
with matching scaled intrinsics when selected. `head_camera_resize` keeps legacy
simulation inference/preview outputs at 320x240. Wrist sensors stay 320x240.
Gazebo still has synthetic intrinsics/FOV; this does not reproduce ZED optical
calibration or differences in FOV between its native capture modes.

The physical ZED Mini configuration (`ffw_bringup/config/common/zedm.yaml`)
remains `general.grab_resolution: VGA`, with NATIVE publication. For HD720 docking,
set `general.grab_resolution: HD720` and restart the camera driver first. This
also changes its native published stream for other consumers. Selecting HD720 in
the action alone cannot recover detail from VGA. No physical device was tested.

Detection and its subscriptions stop on docking completion/failure. Changing
Gazebo sensor resolution requires restarting Gazebo. Older `standard` and
`high_resolution` profile names are read as VGA and HD720, respectively, for
saved-tree compatibility; new trees should use the explicit names above.
