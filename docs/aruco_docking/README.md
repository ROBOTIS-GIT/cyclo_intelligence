# ArUco docking — Gazebo first-stage test

`ArucoDock` is a local image-feedback BT action for the FFW-SG2 holonomic base.
It does not plan a route. Start within 3.5 m, facing a visible marker in a clear
approach area, after stopping Navigation/teleop/inference that commands the base.
Only one docking action may own the base in a Task Engine process.

## Simulation markers

The `home_autonomy` world includes `home_aruco_docks` below the north-wall clock.
From inside the room, left to right: **10, 11, 12**, `DICT_4X4_50`.
Each marker's outer black square is **0.30 m**; white board is 0.40 m.
Centres: `(0.55, 6.875, 1.10)`, `(1.35, 6.875, 1.10)`, `(2.15, 6.875, 1.10)`.
Faces point toward -Y. Small digits below each board identify the marker.
Change `marker_id` to dock to each marker individually; this is not a three-marker
pose-fusion algorithm. The selected marker must be visible.

Assets are generated by `ffw_bringup/tools/build_home_aruco_docks.py` using the
actual OpenCV dictionary. Geometry avoids external texture path problems.

## Canvas usage

Start Task Engine and refresh its node catalog. Add **ArucoDock** to a Sequence
in Action Canvas or a waypoint's local BT in Mission Canvas. No Qwen is needed.
An example lives in `orchestrator/orchestrator/bt/trees/aruco_dock_10.xml`:

```xml
<root BTCPP_format="4" main_tree_to_execute="MainTree">
  <BehaviorTree ID="MainTree">
    <ArucoDock name="DockToMarker10" marker_id="10" marker_size="0.30"
               target_distance="0.85" timeout="120" />
  </BehaviorTree>
</root>
```

- `target_distance`: metres from **base_link origin to marker face**, not camera.
- `position_tolerance`: XY error norm, default 0.035 m.
- `yaw_tolerance`: radians, default 0.06 (~3.4 degrees).
- `max_speed`: combined XY speed limit, default 0.10 m/s (maximum 0.20).
- `max_yaw_rate`: default 0.18 rad/s.
- `min_speed` / `min_yaw_rate`: 0.035 m/s / 0.04 rad/s outside the pose
  tolerance, to exceed the simulation swerve controller's 0.03 component
  deadbands. Inside tolerance the command is zero. These values do not alter
  Navigation or the underlying controller configuration.
- `stable_seconds`: 0.7 s and at least five separate valid frames, with low odometry
  velocity, before SUCCESS.
- `timeout`: 120 s wall time, excluding acknowledged pauses.
- `lost_timeout`: 3 s without usable feedback before FAILURE. Motion stops
  immediately on an unusable observation; it never drives blind to find a marker.

Transport defaults (editable ports): `/zed/left/image_raw`,
`/zed/left/camera_info`, `/scan`, `/odom`, `/cmd_vel`, `base_link`.
These are the simulation topics; real-camera topics/calibration must be configured
and verified before any physical-robot deployment. The raw Image and CameraInfo
must agree on resolution and optical frame. Distorted images use K and D directly.

## Implementation

- `bt/docking_vision.py`: OpenCV 4.6+ detection, ID selection, solvePnP,
  reprojection screening and optical-frame → base-frame transforms.
- `bt/docking_core.py`: marker-normal target pose, bounded holonomic feedback,
  conservative footprint/scan clearance checks.
- `bt/docking_runtime.py`: lazy ROS inputs, image-time TF lookup, timestamp and
  receipt freshness, worker/watchdog, status/preview, acknowledged pause and Stop.
- `bt/actions/aruco_dock.py`: editor ports, lifecycle and BT result.

The face normal is marker +Z. The target lies `target_distance` along that normal
and faces back toward the marker. No known Gazebo marker/world coordinates are
used by the controller. Translation waits when heading error exceeds 0.45 rad.
The exact image-time TF is awaited for up to 0.12 s to accommodate sensor/TF arrival
order; no latest-TF fallback is used. Stale images, odometry, scan, invalid poses,
obstacles or missing markers stop commands. An active NavigateToPose goal rejects
docking. This is local test control, not a certified collision-avoidance system.

## Diagnostics

- `/bt/aruco_docking/status`: JSON with marker ID, phase, error `[x,y,yaw]`, detail.
- `/bt/aruco_docking/debug_image`: selected marker outline and docking error.

Completion requires both geometry and stationary odometry. A successful RESUME
of a VLA is not used as evidence of docking success.

## Verified in the running Home Gazebo scene (2026-10-19)

- Unit/package-boundary tests: 67 passed (15 docking tests).
- IDs 10 / 11 / 12: BT returned SUCCESS using rendered head images and TF.
- Final visual XY error norms: approximately 3.34 / 3.26 / 3.00 cm,
  within the configured 3.5 cm tolerance. These are detector estimates, not
  independently measured physical positioning accuracy.
- ID 11: acknowledged Pause then Resume and completed.
- ID 12: reset/Stop emitted zero velocity and stationary odometry was observed;
  a fresh BT execution completed afterward.
- Absent ID 49: FAILURE after the feedback deadline, without blind searching.
- Actual Task Engine `/bt/nodes/catalog` exposes ArucoDock and its ports;
  `/bt/load_and_run` accepted the XML and `/bt/status` reached `completed`.

This verifies the first simulation path, not statistical reliability or real
hardware operation. Navigation-to-dock handoff and pick/place are subsequent work.

Docking clearance: circular radius 0.43 m + 0.04 m margin + 0.5 s translation lookahead. At 0.035–0.10 m/s the forward check reaches 0.4875–0.52 m. A 0.55 m target is the next simulation test setting; accepting a 0.35 m parameter does not bypass this collision guard. Close-range operation remains unvalidated.

## Rectified docking images

ArucoDock always detects markers in rectified pixels and estimates pose using
CameraInfo.P's left 3x3 matrix with zero distortion. `image_mode="raw"` (default)
rectifies the existing image topic internally using K, D, R and P; maps are cached.
Existing Gazebo missions need no edits. `image_mode="rectified"` skips remapping;
select the matching rectified image and CameraInfo topics together. For ZED the
left rectified topic may be `/zed/zed_node/left/image_rect_color`; verify the driver
CameraInfo topic and calibration before use. Do not apply raw mode to rectified
images, as that would correct distortion twice. Rectified pose is transformed
back using R transpose before the camera-to-base TF. Full-frame left/monocular
calibration is required; ROI/binning and right stereo P translations are rejected.
The debug image is now rectified. Close-range docking remains subject to visibility
and collision checks; rectification does not recover cropped or occluded markers.
